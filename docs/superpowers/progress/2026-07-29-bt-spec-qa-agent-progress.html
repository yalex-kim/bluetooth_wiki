What is actually verified

Worth separating from "what is written", because they are not the same thing.

Verified

  • 96 tests pass (python -m pytest tests -q) — 80 new under tests/qa/, plus the 16 pre-existing tests still green. No network, no endpoint.
  • Real-corpus parse. scripts/qa_ingest.py --version 6.0 --dry-run over sources/specs/6.0/Core_v6.0.md: 5095 sections | 3612 tables | 841 figures | 3685 xrefs → 9549 graph nodes / 11634 edges / 7282 chunks (3612 table chunks). Node count reconciles exactly: 1 document + 5095 + 3612 + 841 = 9549.
  • End-to-end composition (tests/qa/test_end_to_end.py) — real pipeline, stores, actions, loop and service wired together with only the LLM faked. Proves retrieved spec text reaches the model, a genuine citation survives verification with a resolvable path, and a fabricated one is stripped with confidence downgraded.
  • Full write path at real corpus scale — a complete ingest of Core_v6.0.md with a stub embedder (endpoint excluded, everything else real):
    • Pass 1: 5095 sections → 7282 chunks, 11634 edges, 1.3 s excluding embedding.
    • Pass 2 on unchanged input: changed=0, skipped=3164 — the §5.5 incremental gate holds at scale, so a re-ingest costs no endpoint calls.
    • On disk: graph.db 7.1 MB, vectors.npy 1.9 MB, records.json 9.6 MB, manifest.json 0.2 MB.
    • Reload from disk round-trips all 7282 vectors; vector_search across them takes 10 ms, which is what justifies the brute-force numpy backend at Phase 1 volume.
    • get_section_text returns 2492 chars of real spec text; get_table returns a real table with its pipe structure intact and an evidence path that resolves. graph_lookup("CONNECTION STATE") returns 3 distinct nodes — the repeated-name-across-Volumes case, now correctly separate rather than collapsed.
  • Isolation. No import edge between qa/ and agent/ / search/ in either direction.
  • No new dependencies. Imports resolve to stdlib, numpy, openai, fastapi/pydantic/uvicorn, mcp — all already declared in pyproject.toml.
  • Cold start. SpecQAService.from_index() against an empty index directory returns {"status": "empty", "vector_count": 0} instead of crashing.

Not verified

  • No live endpoint run. Every embedding and chat call is faked; there is no .env in the working tree and OPENAI_BASE_URL is empty. Real embedding dimensionality, latency, batch limits, quota behaviour and tool-calling stability are all unmeasured. The §5.3 extraction and §5.4 figure stages have never executed against a model.
  • Table caption extraction is partial. The caption regex expects Table X.Y: …; conversions that render a caption differently fall back to a positional Table N label. The table content and structure are intact — only the human-readable caption degrades — but it will weaken lexical matching on caption-targeted queries.
  • MCP server untested at runtime — the mcp package is not installed in this environment. server/qa_mcp.py defers its MCP imports so the module imports cleanly, but bluetooth-spec-qa-mcp has not been launched.
  • No retrieval-quality measurement. Nothing yet says whether the hybrid retriever answers better than the existing wiki agent. §9's eval sets do not exist for this system.
  • Pre-existing, unrelated: the console script bluetooth-wiki-agent-mcp = "server.mcp:main" points at a server/mcp.py that does not exist. Not introduced here and not touched.

Two real bugs the work surfaced

Both were found by running the code against the actual Core spec rather than by review.

1. Section parentage from heading depth was wrong

Converted Core specs render 4.5 and 4.5.2 both as ###, so a markdown level stack makes them siblings. Parentage now comes from the dotted section number, with the level stack as the fallback for unnumbered headings. Caught by test_headings_become_a_parent_linked_section_tree.

2. Section ids collided across Volumes

Core specs restart section numbering in every Volume/Part, so core-6.0#4.5 occurred dozens of times in one document. The first real dry run showed the symptom plainly: 3612 tables producing 13112 table chunks. Colliding ids meant graph nodes overwrote each other, distinct chunks collapsed onto one id, and citations would have pointed at the wrong Volume. Ids are now disambiguated by line number, and the counts reconcile (7282 chunks, 3612 table chunks).

This invariant is recorded in CLAUDE.md §4.5 so it does not get refactored away.

Decisions taken on the design doc's open issues (§12)

How to run what exists

# parse only — no endpoint calls, reports what would be indexed
python scripts/qa_ingest.py --version 6.0 --dry-run

# build the index (needs OPENAI_BASE_URL + an embedding model)
python scripts/qa_ingest.py --version 6.0
python scripts/qa_ingest.py --version 6.0 --extract --figures   # + LLM stages

# serve
bluetooth-spec-qa-http      # POST /qa/ask, GET /qa/health  (port 8090)
bluetooth-spec-qa-mcp       # MCP stdio, tool: bluetooth_spec_qa

# tests
python -m pytest tests -q

Config is the BT_QA_* block in .env.example. The index is written to qa/index/ (gitignored): vectors/, graph.db, manifest.json, registry.json.

Suggested next steps

Ordered by what unblocks the most. The first item is a prerequisite for judging anything else.

  1. Run Phase 0 against the real endpoint. Start with --version 6.0 and no enrichment flags: it exercises the embedding API 7282 times and will surface dimensionality, batch limits, throughput and quota reality. Then a single /qa/ask call to see the loop and tool-calling behave.
  2. Measure cross-lingual retrieval (§14.10). Korean question, English chunks. The design doc flags this as must-verify and the answer changes the ingest design (query pre-translation vs bilingual chunk text vs a different embedding model).
  3. Check tool-calling stability across the three candidate models (§7.3). The loop assumes reliable function calling; a model that emits malformed tool calls burns the whole budget. The loop already surfaces malformed arguments as an error result rather than crashing, so this is measurable.
  4. Build the eval set (§9). The existing 42-question eval/dataset.json is the natural starting corpus, but it needs the per-type split the design doc asks for — lookup / multi-hop / version-comparison / figure-dependent / out-of-scope negatives — plus the loop metrics (iterations per query, budget-exhaustion rate, p50/p95 latency, tokens per query).
  5. Then decide §12's DB question with real numbers instead of guesses. The protocols mean this can wait until the traffic and re-indexing patterns are known.
One caution for whoever picks this up: the retrieval quality claim is entirely unproven. What is proven is that the plumbing is correct and the guardrails work — citations are checked against real evidence, thin answers report themselves as thin, and out-of-scope questions cost nothing. Whether Vector+Graph actually beats the existing wiki agent on real questions is exactly what step 4 is for, and the design doc's own ablation plan (vector-only / graph-only / hybrid) is the honest way to justify the graph's build cost.
